## Addendum: Game Setup cohesion + contrast pass (2026-08-03, fifth session)

User follow-up (live use of the fourth-session build) reported the Game Setup modal itself "feels like multiple components slapped together," styling wasn't uniform, light text was hard to read on light backgrounds, and player-count (top) vs. name-editing (bottom, separate disclosure) felt disconnected. Re-diffed against `IMG_9509.PNG` and, critically, against this app's *own* other light modal (`CounterPanel.tsx`), which turned out to already have the correct pattern:

- **Root cause of the contrast/uniformity complaints**: `GameSetupPanel` was written when it rendered inline on the tracker's dark page background (first session). When the fourth session wrapped it in a white `GameSetupModal` dialog, its internal Tailwind classes were never re-themed — it kept dark-mode chip colors (`bg-zinc-900`/`border-zinc-700`/`text-zinc-100`) and, for selected/primary controls, `text-accent-soft` (a light pastel meant to pop against a dark background) on a barely-tinted `bg-accent/15-25`. Against the modal's white surface that combination reads as illegible near-white-on-white. `CounterPanel.tsx`, the app's other light modal, never had this problem — it already used `zinc-50/100/200/300` chip colors and `text-accent-strong` for accent text. `GameSetupPanel` is now restyled to match that exact established pattern: unselected pills are `border-zinc-300 bg-zinc-50 text-zinc-700`; selected/primary controls are a solid `bg-accent-strong` fill with `text-accent-contrast` (a token already designed per-palette in `palettes.ts` specifically for readable text on an accent-strong fill), replacing every `accent-soft`-on-light-tint combination in this component.
- **Duplicate header removed**: `GameSetupPanel` rendered its own "Table settings" eyebrow + "Game setup" heading directly beneath `GameSetupModal`'s own "Life Tracker" eyebrow + "Game Setup" heading — the same information twice. `GameSetupPanel` no longer renders a header; it starts directly with the Reset/New Game action row (restyled: Reset as a neutral light button, New Game as the solid accent-strong primary action), then the three settings rows, separated by hairline `divide-y divide-zinc-200` dividers matching `CounterPanel`'s own internal-divider convention instead of nesting a second bordered box inside the modal's box.
- **Player-count vs. name-editing reunified**: previously, the Players pill row (sets count) lived in `GameSetupPanel`, while a separately-styled, still-dark-themed `PlayerRosterEditor` rendered *after* the Layout and Starting-life rows with its own redundant "N players ▸" toggle bar (duplicating the count the pill row above had just shown) before finally exposing per-player name inputs — two different components, two different visual languages, far apart, exactly the "bolted together" and "odd ordering" complaints. Fixed by dropping the tracker's reuse of `PlayerRosterEditor` entirely and building a small "Edit names" disclosure directly into `GameSetupPanel`'s own Players section, immediately below the pill row: a text-button toggle (no redundant count label, since the pill row already shows it) that reveals one light-styled name input per current player, inside the same section/divider block. `PlayerRosterEditor` keeps its original dark styling and full stepper unchanged for its one remaining caller, `MtgAssistantApp` (which renders it inside its own dark `page-card`); the `showCountStepper` prop added in the fourth session specifically to wedge `PlayerRosterEditor` into this call site is reverted since nothing sets it `false` anymore.
- **Not touched**: Layout and Starting-life rows keep their prior behavior/contracts (grid/list toggle, custom-life inline editor) — only their color classes changed to match the corrected light palette. No `GameContext`/persistence/seed contract changes.

## Addendum: mobile-viewport layout fixes (2026-08-03, seventh session)

User follow-up, this time diagnosed live in Chrome (via the Claude-in-Chrome browser plugin) at a genuine ~390px mobile viewport rather than narrated secondhand: three concrete cutoff/overlap defects, each root-caused with actual `getBoundingClientRect()` measurements before any fix landed, per `systematic-debugging`. All three trace to `PlayerLifeCard.tsx`/`PlayerLifeTrackerApp.tsx` decisions made when the table's aspect ratio and available width were implicitly assumed to be tablet/desktop-sized; none are new regressions from a prior session, they're latent since the seat-rotation and center-gear designs were first built.

- **Rotated-card content clipping ("cutoff" complaint)**: `PlayerLifeCard`'s content block (name pill, life number, commander-damage grid) is rotated 90/270deg for left/right-seated players (`seatArrangement`'s left/right columns, used for 4-8 players) but was sized to the card's own un-rotated `width`/`height` via `absolute inset-0`. A 90/270 rotation swaps a box's effective footprint; since grid cards are portrait rectangles rather than square (more so the narrower the viewport, since seats stack 2-per-row on a phone), the rotated content needed more width than the card had and the card's `overflow-hidden` silently clipped it. Reproduced concretely: at the default "Player N" labels the clearance was already only ~3px; renaming a seat to a realistic longer name ("Christopher") measured a 7px clip, visually confirmed as a corner-cropped name pill. Fixed with CSS container queries: the card (`<article>`) gets `container-type: size` (it already had `overflow-hidden`, which is required for size containment to take effect), and the rotated content div sizes itself off `100cqh`/`100cqw` (swapped for 90/270deg seats, unswapped otherwise) instead of the card's own un-rotated `width`/`height` — so the rotated box is always exactly card-sized post-rotation, at any card aspect ratio, any rotation, any content length, with no JS measurement needed. The content div's positioning moved from `inset-0` to `left-1/2 top-1/2` + `translate(-50%, -50%)` (composed with the existing `rotate()`) since explicit non-100% width/height and `inset-0` don't compose.
- **Settings-cog overlap ("out of place... overlapping other elements")**: the "Open game setup" button was `absolute left-1/2 top-1/2` against the entire `<section data-testid="life-tracker-table">` grid — centered on the whole (potentially many-row) table, which reads fine when the table is roughly square and fits one viewport (tablet/desktop), but on a phone the table stacks into several rows taller than the screen, so the button lands mid-scroll directly on top of whichever row is at the grid's vertical midpoint. Measured concretely at 5 players/390px width: the button's box sat squarely inside the Player 2/Player 5 cards' box, obscuring their name pills. This wasn't grid-specific — list mode hit the same bug, since it also centers against a tall single-column stack. Fixed by moving the button out of the grid-relative positioning entirely, into the page header next to the "Player Life Tracker" heading — a normal, always-reachable, non-overlapping control regardless of player count or layout mode, rather than a responsive breakpoint hack that would have to reason about when the whole table does/doesn't fit one screen.
- **List-mode +/- placement**: `PlayerLifeCard`'s decrease/increase bands were hardcoded as full-width top/bottom strips (`inset-x-0 top-0`/`bottom-0`) regardless of layout mode. That reads fine for the portrait grid cards but is awkward on list mode's wide, short, unrotated rows — thin strips at the very top/bottom edge of a wide card instead of natural left/right tap zones. `PlayerLifeCard` now takes an explicit `layoutMode: LayoutMode` prop (threaded from `PlayerLifeTrackerApp`'s `tracker.state.layoutMode` — placement/rotation alone can't disambiguate list mode from a 2/3-player grid seat, since both can have `side: "bottom", rotation: 0`) and renders `inset-y-0 left-0`/`right-0` vertical bands in list mode, keeping the original top/bottom bands unchanged in grid mode.
- **Not touched**: the seat-rotation design itself (`seatArrangement.ts`, REQ-081/DEC-101) is unchanged — rotation toward each seat's table edge is intentional, confirmed-against-reference behavior, not a bug; only the box-sizing math for the already-rotated content was wrong. The `-`/`+` glyph's own rotation (a single character, negligible aspect-ratio risk) is untouched. No `GameContext`/persistence/seed contract changes.

Verified with `getBoundingClientRect()` measurements taken directly in a running Chrome tab before and after the fix (documented above), a full `npm run typecheck` (clean), scoped `eslint` on every touched file (clean), and the full frontend suite (835/835 passing — two new cases added: list-mode band placement, and the sideways-vs-upright `100cqh`/`100cqw` swap).

## Addendum: list layout replaced with the row-based "turned ends" pattern (2026-08-03, ninth session)

User follow-up: the single-column `listSeatArrangement` (one full-width, unrotated card per row, top-to-bottom) reads fine on a tablet but is "basically unusable on phones" - at 6-8 players it's a long uniform scroll of thin rows with no visual grouping. Re-examined `IMG_9509.PNG`'s Layout selector row up close (cropped/upscaled the icon region): the second icon isn't a generic "list" glyph, it depicts three rows - a full-width bar, a pair of half-width tiles, a full-width bar - i.e. the same "symmetric rows, ends turned toward the group's edges" idea `seatArrangement` already uses for its 2-player (top/bottom halves) and 3-player (one top seat spanning the width, two bottom seats paired) layouts, just generalized up through 8 players instead of switching to a column split the way `seatArrangement` does at 4+.

- **New `listSeatArrangement` algorithm** (`seatArrangement.ts`): a single full-width "head" seat (rotation 180, faces the top edge) is always seat 1; the remaining players fill side-by-side pair rows (rotation 0 each); for even player counts, where the remainder divides evenly, the last player becomes a single full-width "foot" seat (rotation 0). No seat is ever rotated 90/270 - everything reads upright or upside-down, never sideways - which is what makes this the phone-friendly option: rows stack vertically instead of requiring wide rotated columns, and total row count is roughly half the old one-row-per-player list (e.g. 8 players: 5 rows instead of 8). `count === 2` and `count === 3` produce byte-for-byte the same shape as `seatArrangement`'s own `twoPlayerLayout`/`threePlayerLayout` (confirmed via `toEqual` in tests) - this isn't a new design, it's that same already-shipped, reference-matched pattern applied uniformly instead of special-cased only at the low end. `seatArrangement()` itself (grid mode, DEC-101) is completely untouched - same functions, same column-split behavior, same tests.
- **Band placement follows seat shape, not just mode**: the old rule ("list mode always gets left/right bands") assumed every list-mode seat was a wide, short row. That's no longer true - the new pair rows are narrow, portrait-ish seats much like a grid seat. `PlayerLifeCard` gained an `isWideSeat` prop (computed in `PlayerLifeTrackerApp` by comparing a seat's `gridColumn` span against the layout's total `columns`); list-mode head/foot seats (`isWideSeat=true`) keep the existing left/right bands, list-mode pair seats (`isWideSeat=false`) get the default top/bottom bands. Grid mode is unaffected - it never looks at `isWideSeat` (band placement there stays the unconditional top/bottom it's always been).
- **Not touched**: `seatArrangement.ts`'s grid algorithm/tests, the `layoutMode: "grid" | "list"` persisted contract (still just those two string values, no migration needed), the Grid/List toggle's labels/icons in `GameSetupPanel`, `CommanderDamageCell`/`CounterPanel`, and the header/settings-modal work from prior sessions.

## Addendum: confirm-before-destroy, flat card style, typed life entry, day/night (2026-08-03, tenth session)

Four pieces of direct user feedback on the shipped tracker, implemented together. All four are additive to the existing contracts; the persisted shape gains three fields and stays backward compatible (an old snapshot without them loads and falls back to the documented defaults rather than being discarded as malformed — `isValidTrackerState` deliberately does **not** validate the new fields, and `loadTrackerState` normalizes them on the way out).

- **Reset / New Game confirm in place** ("a confirmation message of sorts"): both actions destroy work with no undo but fired immediately on one press. Each is now a two-step in-place confirm in `GameSetupPanel`: the first press swaps that button for a `Confirm` + `Cancel` pair and fills a `role="status"` live region with what is about to be lost, stated from the actual `state.ts` behavior — Reset: "every life total goes back to the starting life and all counters clear; players, names, and settings stay"; New Game: "this game is discarded: back to 4 players at 40 life, with names and counters cleared; layout, card style, and day/night tracking stay". Only one confirm can be pending at a time — starting the other one cancels the first — and closing Game Setup unmounts the panel, which drops the pending confirm with it. No `window.confirm`: it can't be styled, can't say what will be lost in the app's own voice, and is a modal-on-modal inside a dialog that already owns focus.
- **Flat card style** ("remove the ombre effect... lotta bright white"): the bright element in `LIFE_TINTS` was the gradient's `via-*-50` mid stop (`via-rose-50`/`via-amber-50`/`via-zinc-50`) — near-white across roughly a third of every card, times up to eight cards. `LIFE_TINTS` is now keyed by `cardStyle` first: `"gradient"` is the byte-for-byte original (so nothing changes for anyone who doesn't opt in — it stays the default, including for every already-persisted game), `"flat"` keeps the same three life states and the same border/text colors and replaces the three-stop ombre with a single solid 300-level tint (`bg-rose-300` / `bg-amber-300` / `bg-accent-soft`). That is lower-luminance than the white mid stop it replaces while still light enough for the near-black state text (`text-rose-950`/`text-amber-950`/`text-zinc-900`) to clear AA at every palette — the darkest `accentSoft` in `palettes.ts` is the coral `255 107 107`, roughly 6:1 against `zinc-900`. This is deliberately a two-option switch, not a theming system: the user asked for "basic customization until we get more built out", so per-player colors/pastels stay deferred per the original non-goals. The control sits in Game Setup's Layout section (the look/layout area) as a labeled "Card style" pill pair — Ombre / Flat — matching how `layoutMode` is already presented one row above.
- **Typed life entry** ("in case I gain 100000 life"): the life number in `PlayerLifeCard` is now a button that swaps into an inline numeric input (tap/click, or keyboard focus + Enter, since it is a real button). Enter or blur commits, Escape cancels (a ref guards the blur that Escape's own unmount fires, so cancel can't be overridden by the commit path). It lives inside the single already-rotated content box, so it rotates with the rest of the card at every seat, and it stays inside the `z-10` content layer beneath the `z-20` +/− bands — the bands keep taking their own taps, and the entry never sits under them. The state layer gains `setPlayerLife`, which — like `adjustPlayerLife` — does not clamp: negative and arbitrarily large totals are both real game states. Empty or non-numeric input cancels instead of writing, and `setPlayerLife` refuses a non-finite value outright, so a NaN can never reach persisted state from either side.
- **Day/night tracking** ("this is a hard mechanic to follow but idk how we can track it more easily"): MTG's day/night is **one game-wide designation that flips**, never a per-player value, so it is modelled as a single `dayNightPhase` on `TrackerState`, not as a per-player field or a counter. It is opt-in via the persisted `dayNightEnabled` setting (default off — most games never touch the mechanic, and an always-present header control would be clutter); when enabled, a compact icon+label control appears in the tracker header next to the ⚙ button, showing the current designation (☀ Day / ☾ Night) and flipping on tap, with an `aria-label` that states the current designation and that pressing flips it. Enabling always starts at day (the game's default designation); disabling leaves the phase alone so re-enabling restores it; Reset returns it to day. **On the "track it more easily" ask specifically: this deliberately does not auto-derive the designation.** Day/night flips on conditions this app has no data for — whether a player cast no spells in their own turn, whether any player cast two or more spells in a turn, or a card explicitly setting it. There is no turn structure, no turn ownership, no spell log, and no card-play events anywhere in the tracker (its entire model is life, counters, commander damage, and seats), so any "automatic" flip would be a guess. A one-tap, always-visible reminder of the current designation is the honest version of the ask; auto-derivation would need a turn tracker first, which is a separate feature and is not in scope here.
- **Preferences survive New Game**: layout mode, card style, and day/night tracking are presentation preferences, not part of the game being discarded, so `startNewGame` now accepts and carries them over (`useLifeTracker.newGame` passes the current ones). Silently reverting a user's explicit look/behavior choices every New Game would just make them re-pick each game.
- **Not touched**: `seatArrangement.ts` (both algorithms), `CounterPanel`, the counter/commander-damage model, the seed/`GameContext` contracts, and the storage key. No migration/version bump was needed — the new fields are additive and defaulted on read.

Verified: `npm --workspace apps/frontend run typecheck` clean, full frontend suite 1057/1057 passing (38 new cases across `state`, `persistence` — including the explicit old-shape-without-the-new-fields load path — `useLifeTracker`, `PlayerLifeCard`, `GameSetupPanel`, and `PlayerLifeTrackerApp`), scoped `eslint` clean on all thirteen touched files.
