# DESIGN-BRIEF: player-life-tracker-refinement

Status: proceeding under explicit user authorization to implement without an interactive approval round (overnight, unattended session — see `README.md` status note). This brief still records the required screenshot-vs-shipped diff and the resulting scope so it can be reviewed after the fact.

## Diff: shipped implementation vs. in-scope reference screenshots

Checked live against a running `npm run dev` build (`localhost:5173`, 4-player game) on 2026-08-03.

### Main tracker layout (`IMG_9504.PNG`)
- **Reference**: the life table is the entire screen. No app header, no visible settings/roster chrome. A thin control bar sits between the two halves (undo, turn counter, history, player-color dots, dice) — those controls map to deferred scope (turn timer/history: `IMG_9510`; dice & misc: `IMG_9512`) and are **not** being added here.
- **Shipped**: `TheJudge` brand block + `Player Life Tracker` heading, then a full `GameSetupPanel` (starting-life presets, commander-damage toggle, custom-life form, Reset/New Game) and the roster editor row, all always visible above the table — the table doesn't dominate the screen the way the reference's does.
- **Fix**: keep the header (an existing accessibility contract — `heading` "Player Life Tracker" is asserted by tests — so it stays, just visually slimmer) but move `GameSetupPanel` + the roster section behind a single collapsed-by-default disclosure (mirrors the existing `PlayerRosterEditor` expand/collapse pattern already in this codebase), so the table is the dominant view by default, closing the largest structural gap without introducing new routing/navigation.

### Life cards (`IMG_9504.PNG`)
- **Reference**: light pastel gradient cards, bold near-black life numbers, light rounded name pill, +/- glyphs as thin bands at the card's top and bottom edges.
- **Shipped**: near-black/zinc cards, white numbers, low contrast; **the life number visually overlaps the rotated name pill and the "Counters" button** at default card height (a real readability bug, independent of the reference match — confirmed live in the browser, not just from source); +/- tap zones are on the left/right vertical thirds, not top/bottom.
- **Fix**: light pastel gradient background (state-tinted: healthy/critical/dead, via the existing `--accent` tokens so the user's chosen theme palette still applies) with dark text; move the "Counters" affordance into the same rotated flex content block as the name pill and life number (instead of an independently fixed-position button) so nothing collides at any rotation; move +/- tap zones to top/bottom bands.
- **Scoped out**: the reference's compact 2×2 "mini commander-damage preview" tile embedded on the card face. It only has a clean 2×2 shape for exactly 4 players — 2/3/5–8-player games would need a different, undesigned layout, and the existing "Counters" button already exposes the same data. Left as a follow-up idea rather than shipping a half-designed variant. Per-seat "different pastel per player" is also not replicated — in the reference it most likely reflects either per-card randomness or the deferred winner/reset-with-winner state (`IMG_9508`, `Player 4` shown desaturated with a trophy badge), not a deliberate design system worth reverse-engineering.

### Counter panel (`IMG_9505.PNG` / `IMG_9506.PNG`)
- **Reference**: light modal, vertical Player/Counters tab bar on the right edge, icon-forward tiles for each named counter.
- **Shipped**: dark zinc modal, horizontal top tab bar, text-only tiles.
- **Fix**: flip to a light card matching the tracker's new palette; add a small icon glyph per named counter tile (Monarch/Treasure/Poison/etc.) alongside the existing text label (label text and all `aria-label`s unchanged, so this is additive only).
- **Scoped out**: converting the tab bar to a vertical right-side layout — real value, but lower priority than the color/contrast/icon fixes and a separate structural change; left as a follow-up.

### Settings (`IMG_9509.PNG`)
- **Reference**: dedicated dark full-screen "Settings" page: Players as a 2–6 pill row, a Layout selector (grid vs. list), Starting-life pill row, then a "Gameplay" section of iOS-style toggle rows (Planechase/Archenemy/Bounty/Auto-KO/Commander-damage-life-loss/Turn timer/Game history).
- **Shipped**: `GameSetupPanel` embedded inline as one card; starting-life presets already closely match the reference's pill style. Player-count uses a +/- stepper (in the shared `PlayerRosterEditor`, reused by MTG Assistant — not tracker-specific).
- **Fix**: restyle `GameSetupPanel`'s existing rows (starting-life pills, commander-damage-to-life control) to the reference's iOS list-row look, and move it behind the new collapsed-by-default disclosure described above.
- **Scoped out**: a Layout selector (grid vs. list) — the tracker only implements one layout algorithm (`seatArrangement`); building a second layout mode is new functionality, not a styling refinement. Restyling the player-count stepper into 2–6 pills — that control lives in the shared `PlayerRosterEditor`, also used by MTG Assistant, and changing its visual language would leak into that unrelated screen. The Gameplay toggle rows (Planechase/Archenemy/Bounty/Turn timer/Game history/full Auto-KO) — these map to features that are either explicitly deferred (`README.md`: game history, mana counter, full auto-KO) or were never implemented at all for this feature; adding UI for capabilities that don't exist would be scope creep, not refinement.

## Addendum: commander-damage/counters follow-up pass (2026-08-03, second overnight session)

The first pass above shipped the main-layout and life-card fixes; user follow-up review (live on the shipped build) called out that the counter/commander-damage menus specifically still didn't resemble `IMG_9505.PNG`/`IMG_9506.PNG`. This addendum reverses two items the original brief scoped out, at explicit user request, and stays inside the same non-goals (no `GameContext`/persistence/seed contract changes, no new counter mechanics):

- **On-card commander-damage entry point** (`IMG_9504.PNG`'s small grid of boxes at the corner of each life card, previously scoped out above as "no clean layout for non-4-player counts"): implemented as a read-only preview grid (one "me" tile + one tile per opponent, showing each opponent's current commander-damage value) that replaces the old text-only "Counters" button. Column count is `ceil(sqrt(seatCount))` so it degrades to a clean near-square grid at any supported player count (2-8), not just 4 — verified live at 4 and 6 players with no collision against the life number/name pill. The whole grid is one button (`aria-label="Open counters for {name}"`, unchanged) that opens the same counter panel; it doesn't add its own increment/decrement behavior on the card face.
- **Named-counter tile treatment** (`IMG_9505.PNG`/`IMG_9506.PNG`): named/custom counter tiles are now icon-forward and ghosted (grayscale icon, muted label/value) at zero, becoming colored/highlighted once incremented — matching the reference's "Poison" activated-tile look. The commander-damage matrix tiles keep the original value-forward look (pastel accent tiles, always-visible number), which already matched the reference.
- **Not touched**: the horizontal top tab bar (Player/Counters) stays horizontal — converting it to the reference's vertical right-edge tab bar remains its own follow-up (unchanged from the original scope-out above); no reference screenshot of the "Counters" tab's alternate content exists to confirm a redesign there beyond the icon/ghosting pass already done.

## Addendum: Game Setup pass (2026-08-03, third session)

User follow-up pointed at `IMG_9509.PNG` again, scoped this time to just the **Game Setup** section of that reference (Players / Layout / Starting life) — the `Gameplay` section below it (Planechase, Archenemy, Bounty, Auto-KO, Commander damage life loss, Turn timer, Game history) is explicitly out of scope, consistent with the original brief's scope-out (those map to deferred/nonexistent features). This addendum reverses one more previously-scoped-out item at explicit user request, after confirming intent via a direct question:

- **Players row**: `GameSetupPanel` gets a new pill row (icon + horizontal pills) driven directly by `tracker.state.playerCount` / `tracker.setPlayerCount`, matching the reference's pill treatment. Extended to the app's real supported range (2-8) rather than the reference's 2-6, since the tracker already supports up to 8 seats (`seatArrangement`/`MAX_PLAYER_COUNT`) and truncating that to match the photo would be a functional regression, not a refinement.
  - The existing `PlayerRosterEditor` (shared with MTG Assistant) keeps its own player-count affordance in the UI, since it doubles as the entry point for per-player name editing and MTG Assistant relies on it unchanged. To avoid two live +/- controls for the same value stacked in the same disclosure, it gains an additive, backward-compatible `showCountStepper` prop (default `true`, same pattern as the existing `showLifeTotals` prop) that the tracker sets to `false` — hiding just the +/- buttons there while keeping the count label and the name-editing expand toggle. MTG Assistant's usage is unaffected (prop omitted → default `true`).
- **Layout row**: **reversing** the original brief's scope-out. Per explicit user decision (asked directly, since this touches the locked `seatArrangement` contract / DEC-101), this ships as a real functional Grid/List toggle, not a visual-only stub:
  - `seatArrangement()` (grid) is untouched — same signature, same tests, still the sole grid algorithm.
  - A new, separate `listSeatArrangement(count)` is added to the same module: a single-column, unrotated, top-to-bottom stack (`side: "bottom"`, `rotation: 0` for every seat), 2-8 supported, `RangeError` otherwise — mirrors the existing contract's shape/validation style without touching it.
  - `TrackerState` gains a `layoutMode: "grid" | "list"` field (default `"grid"`), a `setLayoutMode` state transition, and a `useLifeTracker().setLayoutMode` action. `persistence.ts`'s `isValidTrackerState`/load path normalizes missing or invalid `layoutMode` in old persisted saves to `"grid"` rather than rejecting the whole saved game.
  - `PlayerLifeTrackerApp` picks `seatArrangement` vs. `listSeatArrangement` off `tracker.state.layoutMode` when computing the table layout.
- **Starting life row**: already close to the reference (pill row); no structural change, minor polish only if needed to sit visually consistent with the two new rows above it.
- **Scope held from the original brief**: still no Gameplay-section toggles (Planechase/Archenemy/Bounty/Auto-KO/Turn timer/Game history) — those remain deferred/non-existent features, adding UI for them would be scope creep. Still no dedicated full-screen "Settings" route — this stays behind the existing collapsed-by-default disclosure (`isSettingsExpanded`) rather than becoming its own page/navigation.

## Addendum: Game Setup simplification + discrete entry point (2026-08-03, fourth session)

User follow-up trimmed scope further and reversed one more previous decision, based on live use of the third-session build:

- **Custom starting life**: the dedicated custom-life form (separate labeled input + "Apply" button, full-width) is removed outright — too much surface for a rarely-used path. Re-reading `IMG_9509.PNG`: the "60" pill in the reference isn't a fifth fixed preset, it's the **custom slot** displaying whatever custom value was last set (the "Custom" text beneath the row is that slot's label) — a fixed "60" preset was a misread of the reference, not an intentional addition. Fixed presets are now `[20, 25, 30, 40]` only; the 5th slot in the same pill row is a `Custom` pill: it reads "Custom" and sits unselected while `startingLife` is one of the four fixed presets, and reads the active number and sits selected the moment `startingLife` is anything else. Tapping it turns that one pill into a small inline numeric input (same 1-999 validation as before) instead of opening a separate form; submitting (Enter or blur-confirm) applies the value and collapses back to a pill, matching the reference's compactness.
- **Commander damage always reduces life**: the "Commander damage also reduces life" toggle is removed — per explicit user instruction, commander damage should unconditionally reduce life, not be an optional table setting. `commanderDamageToLife` is removed from `TrackerState` entirely (field, default, setter, persistence check, `useLifeTracker` action, `GameSetupPanel` row); `setCommanderDamage`'s life-reduction branch drops the flag check and always applies on a positive increase.
- **Discrete Game Setup entry point**: the wide, always-visible "⚙ Game setup ▸" bar is replaced with a small circular icon-only button, floating centered over the life table (absolutely positioned at the table's midpoint, above the seat cards) — echoing where the reference's "4" control-bar button sits between the two table halves in `IMG_9504.PNG`. This is a **reversal** of the first-session decision not to add a mid-table control bar: that decision was about the reference's full control bar (undo/history/dice/player-color dots), which stays out of scope — only the settings-entry button itself is being added here, confirmed directly with the user rather than assumed. Tapping it opens Game Setup (the same `GameSetupPanel` + roster-editor content as before) as a modal dialog, mirroring the existing `CounterPanel` overlay pattern (backdrop, `role="dialog"`, Escape-to-close, focus return) instead of the old inline expand-in-place disclosure — consistent with how the rest of the app already presents on-demand panels.

## Addendum: Game Setup cohesion + contrast pass (2026-08-03, fifth session)

User follow-up (live use of the fourth-session build) reported the Game Setup modal itself "feels like multiple components slapped together," styling wasn't uniform, light text was hard to read on light backgrounds, and player-count (top) vs. name-editing (bottom, separate disclosure) felt disconnected. Re-diffed against `IMG_9509.PNG` and, critically, against this app's *own* other light modal (`CounterPanel.tsx`), which turned out to already have the correct pattern:

- **Root cause of the contrast/uniformity complaints**: `GameSetupPanel` was written when it rendered inline on the tracker's dark page background (first session). When the fourth session wrapped it in a white `GameSetupModal` dialog, its internal Tailwind classes were never re-themed — it kept dark-mode chip colors (`bg-zinc-900`/`border-zinc-700`/`text-zinc-100`) and, for selected/primary controls, `text-accent-soft` (a light pastel meant to pop against a dark background) on a barely-tinted `bg-accent/15-25`. Against the modal's white surface that combination reads as illegible near-white-on-white. `CounterPanel.tsx`, the app's other light modal, never had this problem — it already used `zinc-50/100/200/300` chip colors and `text-accent-strong` for accent text. `GameSetupPanel` is now restyled to match that exact established pattern: unselected pills are `border-zinc-300 bg-zinc-50 text-zinc-700`; selected/primary controls are a solid `bg-accent-strong` fill with `text-accent-contrast` (a token already designed per-palette in `palettes.ts` specifically for readable text on an accent-strong fill), replacing every `accent-soft`-on-light-tint combination in this component.
- **Duplicate header removed**: `GameSetupPanel` rendered its own "Table settings" eyebrow + "Game setup" heading directly beneath `GameSetupModal`'s own "Life Tracker" eyebrow + "Game Setup" heading — the same information twice. `GameSetupPanel` no longer renders a header; it starts directly with the Reset/New Game action row (restyled: Reset as a neutral light button, New Game as the solid accent-strong primary action), then the three settings rows, separated by hairline `divide-y divide-zinc-200` dividers matching `CounterPanel`'s own internal-divider convention instead of nesting a second bordered box inside the modal's box.
- **Player-count vs. name-editing reunified**: previously, the Players pill row (sets count) lived in `GameSetupPanel`, while a separately-styled, still-dark-themed `PlayerRosterEditor` rendered *after* the Layout and Starting-life rows with its own redundant "N players ▸" toggle bar (duplicating the count the pill row above had just shown) before finally exposing per-player name inputs — two different components, two different visual languages, far apart, exactly the "bolted together" and "odd ordering" complaints. Fixed by dropping the tracker's reuse of `PlayerRosterEditor` entirely and building a small "Edit names" disclosure directly into `GameSetupPanel`'s own Players section, immediately below the pill row: a text-button toggle (no redundant count label, since the pill row already shows it) that reveals one light-styled name input per current player, inside the same section/divider block. `PlayerRosterEditor` keeps its original dark styling and full stepper unchanged for its one remaining caller, `MtgAssistantApp` (which renders it inside its own dark `page-card`); the `showCountStepper` prop added in the fourth session specifically to wedge `PlayerRosterEditor` into this call site is reverted since nothing sets it `false` anymore.
- **Not touched**: Layout and Starting-life rows keep their prior behavior/contracts (grid/list toggle, custom-life inline editor) — only their color classes changed to match the corrected light palette. No `GameContext`/persistence/seed contract changes.

Verified live in Chrome against the running dev build (name editing under Players, custom starting-life inline editor, Grid/List toggle, Reset/New Game) and against `833/833` passing frontend tests, a clean `typecheck`, and clean scoped `eslint` on every touched file.
