# Future-infra finding — rag-data-plane

- Concern-area focus: where rule/ruling embeddings and the retrieval index should live once "RAG for rules" replaces today's keyword/IDF scoring.
- Reference read: `docs/aws/deployment.md`, `scripts/aws-bootstrap.sh`, `scripts/package-lambda.sh`, `scripts/lambda-package-budget.test.mjs`, `PRD/sections/system-map.md`, `apps/backend/src/gameRulesRetrieval.ts`, `apps/backend/src/gameRules.ts`, `apps/backend/src/cardRulings.ts`, `apps/backend/src/runtime/createConfiguredApp.ts`, `apps/backend/data/*` (sized directly).

## Current state

Retrieval today is keyword/IDF scoring over static JSON, not embeddings. Three data files back it:

- `apps/backend/data/gameRulesRuleIndex.json` — 2.2 MB, **3,432 entries** (`node -e` count), one per MTG Comprehensive Rules paragraph (`ruleId`, `sectionTitle`, `text`, `searchText`, `parentRuleIds`). This is the corpus "RAG for rules" would embed for System 3 (supplemental) retrieval.
- `apps/backend/data/gameRulesTokenStats.json` — 256 KB, precomputed per-token document frequency (`N=3432`) for IDF weighting.
- `apps/backend/data/cardRulingsByOracleId.json` — 19.5 MB, **19,542 oracle IDs / 76,605 individual rulings** (counted directly). Looked up by exact oracle ID today (`cardRulings.ts`), not retrieved by relevance — but it is the obvious second corpus if RAG scope ever grows past the rules text.

All three load via `readFileSync` + `JSON.parse` **once, at cold start**, inside `createConfiguredApp()` (`apps/backend/src/runtime/createConfiguredApp.ts:20-27`) — not per-request. `gameRulesRetrieval.ts` additionally caches the parsed rule index and token stats in module-scope `Map`s (`ruleIndexCache`, `tokenStatsCache`), so a warm instance never re-parses. Scoring itself (`scoreIndex` in `gameRulesRetrieval.ts:329-360`) is a linear scan of all 3,432 entries per request — brute-force, in-process, no index structure beyond the token→df map.

The Lambda this runs in: `thejudge-api`, `nodejs24.x`, `arm64`, **512 MB memory**, 20 s timeout, no VPC attachment (`scripts/aws-bootstrap.sh:143-144` — no `vpc`/`efs` config anywhere in bootstrap, confirmed by grep), reserved concurrency 5 (currently unset — account concurrency floor of 10 blocks it per `docs/aws/deployment.md:155-161`). Monthly AWS Budget alarm is **$5** (`scripts/aws-bootstrap.sh:21`, `BUDGET_LIMIT_USD` default). That budget and the reserved-concurrency-5 target are the traffic signal: this is a scale-to-zero hobby app, not a provisioned service.

Deploy-side ceiling: the S3-staged deploy just landed raises the effective package quota from ~50 MB (direct `--zip-file` upload) to Lambda's real **250 MB unzipped** quota (`docs/aws/deployment.md:51-60`, enforced pre-merge by `scripts/lambda-package-budget.test.mjs`). That test's own budget math reserves 20 MB for code/deps and treats everything else as committed-data headroom — currently ~50 MB of committed data (dominated by the two Commander Spellbook combo files, `commanderSpellbookCombos.json.gz` 37.5 MB + `commanderSpellbookComboIndex.json.gz` 2.7 MB, which are a separate combo-lookup feature, not rules retrieval). So there is real headroom (~180 MB) for a rules-retrieval upgrade before the 250 MB quota becomes a constraint again.

## Recommendations

### rag-vectors-bundled-via-s3-staged-deploy — Bundle rule-level embeddings the same way as today's JSON — with-rag

**Current -> Target:** Today: 3,432 rule entries, IDF-scored, bundled as JSON in the deploy package, loaded once at cold start into a module-scope cache. Target: the same 3,432 entries carry a precomputed embedding vector, loaded the same way, scored by brute-force cosine similarity (or a hybrid IDF+cosine blend) instead of pure keyword IDF.
**Gap:** No embedding generation pipeline exists yet (would sit alongside `scripts/build-game-rules.mjs`, which currently only builds the JSON/IDF artifacts per `scripts/*.mjs:build-game-rules.mjs:343-346`). No vector storage format exists — this needs to be added.
**Services/tradeoff:** No new AWS service. Reuses the exact deploy path that just shipped: pack the vectors into `apps/backend/data/`, let `package-lambda.sh` zip them, let `aws-deploy.sh` stage-and-upload via S3. At 3,432 rules, even a generous 1536-dim embedding (OpenAI `text-embedding-3-small`) is **~21 MB as raw float32 binary** (3,432 × 1536 × 4 bytes) — trivial against both the 250 MB deploy quota and the 512 MB Lambda memory ceiling, and small enough that cold-start read/parse cost stays in the tens-of-milliseconds range, not seconds. Brute-force cosine over 3,432 vectors is a few thousand dot products per request — sub-millisecond on Lambda's arm64, no ANN index needed at this corpus size. Cost delta: $0 infra (same S3 artifact bucket, same Lambda) plus flat per-embedding-call OpenAI cost only when the corpus is rebuilt, not per request.
**Risk:** This only holds while the embedded corpus stays at rules-paragraph scale (~3-4k entries). If RAG scope grows to also embed the 76,605-ruling corpus (see `rulings-corpus-scope-decision` below), the math changes by roughly 20x and this recommendation needs revisiting.

### rulings-corpus-scope-decision — Decide whether RAG-for-rules embeds rulings too, before sizing the data plane — with-rag

**Current -> Target:** Current: `cardRulingsByOracleId.json` (19.5 MB, 76,605 rulings) is looked up by exact oracle ID only (`cardRulings.ts:71-83`, a `Map` keyed on oracle ID) — never relevance-scored. Target: unstated. The task brief says "RAG for rules... over the MTG Comprehensive Rules **and rulings corpus**," but nothing in the repo commits to embedding all 76,605 individual ruling comments versus keeping rulings as today's exact-match lookup and scoping semantic retrieval to the 3,432-entry rules corpus alone.
**Gap:** This is a product/scope decision, not an infra one — but it is the single biggest lever on which data-plane option is correct. At 76,605 chunks and the same 1536-dim float32 embedding, the rulings corpus alone is **~470 MB of vectors** — over the 250 MB deploy quota on its own and close to the entire 512 MB Lambda memory budget before code, deps, or the rules vectors are even counted. That forecloses "bundle everything in the zip" and pushes toward S3-cold-load-only (skip the deploy package entirely, `GetObject` from S3 into memory at cold start) or a smaller embedding dimension / dimensionality reduction, or leaving rulings on today's exact-match path and only semanticizing the rules corpus.
**Services/tradeoff:** No AWS service choice is made here — this is the fork in the road that determines whether `rag-vectors-bundled-via-s3-staged-deploy` (in-package) or a leaner "S3 object, `GetObject` at cold start, never touch the deploy zip" variant is correct. Flagging now so the RAG design brief sizes the corpus explicitly instead of discovering the 470 MB figure mid-implementation.
**Risk:** Left undecided, a rulings-embedding effort could silently blow both the 250 MB deploy quota (`lambda-package-budget.test.mjs` would fail the build, which is the intended catch) or the 512 MB memory ceiling (which has no automated guard today — an OOM cold start, not a caught build failure).

### reject-managed-vector-services-at-this-scale — Do not reach for OpenSearch Serverless, Aurora Serverless v2 pgvector, or Bedrock Knowledge Bases at current traffic — now (as a decision, to close off the option before RAG design starts)

**Current -> Target:** Current: zero managed data-tier services — the whole backend is one Lambda plus SSM for the API key. Target: stays that way for the rules/rulings vector store; no managed vector database.
**Gap:** None to close — this is a "don't build" recommendation, grounded in the traffic and budget this app actually has: reserved concurrency of 5 (`aws-bootstrap.sh:20`), a **$5/month** total budget alarm (`aws-bootstrap.sh:21`), and no VPC today.
**Services/tradeoff:** Each managed option has a cost or operational floor that is disproportionate to a $5/month, scale-to-zero app: OpenSearch Serverless bills a minimum of 2 OCUs even fully idle (list-priced in the hundreds of dollars/month — multiples of this app's entire budget). Aurora Serverless v2 has no true pause/scale-to-zero (unlike Aurora Serverless v1); its 0.5-ACU floor still bills continuously, again well past $5/month, and it would be the first stateful/always-on component this stack has ever had. Bedrock Knowledge Bases doesn't remove this cost — it's a managed pipeline *on top of* one of OpenSearch Serverless / Aurora / Pinecone as the actual vector store, so it inherits whichever backing store's floor plus its own per-query/per-ingestion charges. DynamoDB has no native vector-similarity query (no ANN, no cosine operator) — using it here would mean fetching all items and computing similarity in Lambda anyway, which is strictly worse than bundling/S3-loading a flat file: same brute-force compute, plus per-item network round-trips and DynamoDB request cost for no retrieval-quality benefit.
**Risk:** None from not adopting these now. Revisit only if traffic grows enough (sustained concurrent load, not occasional personal use) that the $5 budget itself gets revised upward — a scale change this app shows no sign of.

### binary-not-json-vector-format — When vectors are added, store them as raw binary, not JSON float arrays — with-rag

**Current -> Target:** Current: every existing data artifact (`gameRulesRuleIndex.json`, `gameRulesTokenStats.json`, `cardRulingsByOracleId.json`) is plain JSON — fine for strings/ints/small floats. Target: embedding vectors stored as a raw `Float32Array` binary blob (e.g. one `.bin` file of concatenated vectors + a small JSON/`.bin` sidecar for row->ruleId mapping), not JSON arrays of floats.
**Gap:** No such format exists yet in the build pipeline; `scripts/build-game-rules.mjs` only emits JSON today.
**Services/tradeoff:** JSON-encodes a float as text (`-0.083452177`, ~11-13 bytes) versus 4 bytes for a binary float32 — roughly a 3x size penalty for no benefit once the consumer is trusted first-party code reading its own artifact. At the 3,432-rule scale this doesn't matter (2 MB vs 21 MB either way); at ruling-corpus scale (see above) it's the difference between ~470 MB and >1 GB, which matters a great deal against both the 250 MB deploy quota and 512 MB Lambda memory. `node:fs` + a typed-array view (`Buffer` -> `Float32Array`) reads binary just as easily as `JSON.parse` reads text, so this costs nothing operationally.
**Risk:** Low — this is a format choice available with no infra change, worth deciding once (before the first embedding build script is written) rather than migrating a shipped format later.

### embedded-ann-store-if-corpus-grows — LanceDB/sqlite-vss stays a documented fallback, not a default — later

**Current -> Target:** Current: not needed — brute-force cosine over ~3,432 vectors in Lambda memory is fast enough that no index structure is justified. Target: unchanged unless the embedded corpus grows past comfortable brute-force bounds (rough rule of thumb: tens of thousands of vectors, where a linear scan starts costing meaningful per-request CPU/latency inside the 20 s Lambda timeout).
**Gap:** None today. Flagging this only so it isn't reinvented as a "we need a vector database" reflex the first time the rulings-corpus-scope question above resolves toward "yes, embed rulings."
**Services/tradeoff:** An embedded ANN library (LanceDB, sqlite-vss) run in-process avoids every managed-service cost floor from the rejection above — it is a library, not a service, so scale-to-zero is unaffected. Two hosting shapes: (a) baked into the deploy package/container image, same as today's JSON — fine up to the 250 MB deploy quota; (b) mounted via EFS for a larger index than the deploy quota comfortably holds. (b) is the one with a real new cost: this Lambda has **no VPC attachment today** (confirmed absence in `aws-bootstrap.sh`), and EFS requires the Lambda to run inside a VPC. That adds ENI cold-start attachment overhead (historically Lambda's worst cold-start tax before Hyperplane ENIs, now much smaller but non-zero) and, because the Lambda still needs a public path to call the OpenAI API, either a NAT Gateway (recurring hourly cost, likely exceeding the entire $5 budget on its own) or a VPC endpoint plus careful egress routing. This is real operational weight this app does not carry today.
**Risk:** Premature adoption risk only — building VPC/EFS plumbing before the corpus size actually demands it. No risk in deferring.

## Open questions

- Does "RAG for rules" (per the forcing-function framing) mean embedding the 3,432-entry Comprehensive Rules corpus only, or also the 76,605-entry rulings corpus? This single decision changes the vector-store size by ~20x and determines whether "bundle in the deploy zip" or "S3-load-only, skip the zip" is the right shape. Not answerable from the repo as it stands — the code path shows rulings as exact-oracle-ID lookup only, with no relevance-scoring precedent to extrapolate from.
- What embedding model/dimension is intended? This finding assumes OpenAI `text-embedding-3-small` (1536-dim) as a size reference since the app already calls OpenAI (`ASK_AI_PROVIDER=openai`, `docs/aws/deployment.md:33`); a smaller dimension (e.g. `text-embedding-3-small` truncated, or a 384-dim open model) would shrink every size figure above proportionally, and is worth deciding before committing to a storage format.
- Whether hybrid retrieval (today's IDF/keyword scoring blended with cosine similarity, rather than a full replacement) is the intended target — the task framing says "semantic/hybrid," and if the IDF path is kept alongside embeddings, `gameRulesTokenStats.json`/`gameRulesKeywordVocabulary.json` stay in the data plane rather than being retired, which is a smaller migration than a full cutover.
