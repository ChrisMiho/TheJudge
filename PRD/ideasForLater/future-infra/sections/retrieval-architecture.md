# Future-infra finding — retrieval-architecture
- Concern-area focus: moving System 3 supplemental rules retrieval from keyword/IDF lexical scoring to semantic/hybrid retrieval ahead of "RAG for rules."
- Reference read: `apps/backend/src/gameRulesRetrieval.ts`, `gameRulesTopicSelection.ts`, `gameRules.ts`, `cardRulings.ts`, `PRD/sections/system-map/game-rules-retrieval.md`, `PRD/sections/system-map.md`, `PRD/sections/decisions.md` (DEC-045/046/047), `apps/backend/src/eval/contextEvaluationHarness.ts`, `apps/backend/src/eval/relevanceReport.test.ts`, `scripts/compare-combo-answer-quality.mjs`, `docs/aws/deployment.md`, `docs/aws/secrets.md`, `scripts/package-lambda.sh`, `scripts/lambda-package-budget.test.mjs`, `apps/backend/data` (`ls -la`, entry counts read via `node -e`).

## Current state

A player's question is answered by one Express Lambda (`thejudge-api`, nodejs24.x, arm64, **512 MB**, **20 s** timeout, reserved concurrency 5 — `docs/aws/deployment.md`) that grounds its OpenAI call in three reference systems assembled at prompt-build time, all in-process, no network calls:

- **System 1 — card rulings** (`apps/backend/src/cardRulings.ts`): exact-match lookup by oracle ID against `apps/backend/data/cardRulingsByOracleId.json` (**19.5 MB** on disk, 19,542 oracle IDs, 76,605 individual WotC ruling entries). This is not retrieval in the RAG sense — it's a keyed dictionary lookup for cards already present in the submitted game state — so it stays out of scope for embedding/chunking work, but its corpus size matters for any "embed all rulings text" recommendation below.
- **System 2 — curated baseline** (`gameRulesTopicSelection.ts`, `gameRules.ts`): a fixed rule-based topic selector keyed only on `turnPhase`, `combatStep`, and populated-zone presence (never card text or keywords). Selects from `gameRulesByTopic.json` (25.8 KB, ~topic manifest `gameRulesTopicManifest.json` is 3 KB). This is deterministic and out of scope for semantic retrieval — it is not scored, it is state-machine selection.
- **System 3 — supplemental retrieval** (`gameRulesRetrieval.ts`, 478 lines): the actual keyword/IDF system this concern-area targets. It tokenizes the question + oracle/context text (`tokenize()`, `[^a-z0-9.]+` split, stopword list, min length 3), scores every entry in `gameRulesRuleIndex.json` (**2.2 MB**, **3,432 rule entries**, avg 240 chars/entry, ~823K chars of rule text total — small corpus) with `IDF = log(N / df)` from a precomputed `gameRulesTokenStats.json` (256 KB), applies a `QUESTION_TOKEN_MULTIPLIER = 3` and `KEYWORD_TOKEN_MULTIPLIER = 6` from a 328-byte keyword vocabulary file, adds `SCORE_EXACT_RULE_ID = 100` / `SCORE_PARENT_RULE_ID = 20` bonuses for explicit rule-number mentions, excludes rule IDs already selected by System 2, and returns the top 5 by score (`retrieveSupplementalRules`, ties broken by IDF then ascending rule ID).

This is pure lexical scoring — **no embeddings, no vector store, nothing that calls an external model at request time.** Everything loads once at cold start (`ruleIndexCache`, `tokenStatsCache`, `keywordVocabularyCache` — module-level `Map`s) and is O(index length × query tokens) per request, all in-memory, no I/O in the hot path.

**Eval harness today**: `apps/backend/src/eval/contextEvaluationHarness.ts` + `relevanceReport.test.ts` (DEC-047, REQ-032) is a deterministic, exact-match golden-fixture harness. Each of the ~30 fixtures under `apps/backend/src/eval/fixtures/` can carry an `expected` block (`expectedSystem2TopicIds`, `expectedSupplementalRuleIds`, `forbiddenSupplementalRuleIds`) checked as **recall hits / excluded noise** against the top-5 rule-ID list, plus exact-string `.prompt.golden.txt` snapshots of the assembled prompt. This is separate from `scripts/compare-combo-answer-quality.mjs`, which is an unrelated, informational, opt-in (`--confirm-live-calls`) side-by-side LLM-answer comparison for combo enrichment, not rules retrieval — it gates nothing and asserts no golden.

**Deploy headroom**: the Lambda zip is built by `scripts/package-lambda.sh`, which copies `apps/backend/data` verbatim into the package. Current package is ~50-55 MB against the new **250 MB unzipped** quota (`scripts/lambda-package-budget.test.mjs`, enforced pre-merge) — roughly 195 MB of headroom exists today for a bundled vector index, before touching the S3-staging change that unlocked it.

**Secrets/provider plumbing today**: `OPENAI_API_KEY` is already an SSM `SecureString` read at cold start into `process.env` (`docs/aws/secrets.md`), used via `ASK_AI_PROVIDER=openai` for the answer-generation call. No embedding-specific credential or Bedrock IAM grant exists yet — `cardRulings.ts` / `gameRulesRetrieval.ts` do zero network calls.

Open question already on record: `system-map/game-rules-retrieval.md` flags **Q-001** (System 3's keyword-vocabulary derivation strategy) as unresolved — relevant context, not something this study resolves.

## Recommendations

### RA-001 — Build-time embedding generation, not runtime — with-rag
**Current -> Target:** Today System 3 does zero embedding/network work per request — all scoring is precomputed IDF stats loaded at cold start. Target: when RAG lands, rule/ruling chunk embeddings are generated **offline** (a data-pipeline script, analogous to how `gameRulesRuleIndex.json` and `gameRulesTokenStats.json` are already precomputed artifacts) and shipped as a static vector index bundled in `apps/backend/data`, not computed per-request in the Lambda.
**Gap:** No embedding pipeline exists yet in this repo. The precedent (precomputed IDF/keyword-vocab JSON, loaded once at cold start) is the right shape to extend, not replace.
**Services/tradeoff:** Runtime (query-time) embedding of the *rule corpus* would require the Lambda to call an embedding API on every cold start or every request, adding latency inside the existing 20 s timeout and defeating the current scale-to-zero, no-network-in-the-hot-path design. Build-time embedding costs nothing at request time and keeps the 512 MB/20 s budget for the query embedding call only (one small embedding call per question, not per corpus). Query-time embedding of the *user's question* is unavoidable and small (single short string).
**Risk:** Corpus updates (new Comprehensive Rules release, new rulings batch) now require an offline re-embed step before deploy, not just a JSON regen — adds a pipeline dependency the current System 2/3 data build doesn't have today.

### RA-002 — OpenAI embeddings over Bedrock Titan/Cohere for the first cut — with-rag
**Current -> Target:** No embedding provider is wired in today. Target: reuse the existing OpenAI relationship (`text-embedding-3-small` or similar) rather than introducing AWS Bedrock for embeddings.
**Gap:** Zero embedding provider exists; this is a build decision, not a migration.
**Services/tradeoff:** OpenAI embeddings reuse the exact secret plumbing already live — `OPENAI_API_KEY` from SSM SecureString (`docs/aws/secrets.md`), same `ASK_AI_PROVIDER` config pattern, zero new IAM grants. Bedrock Titan/Cohere embeddings avoid a second external dependency and use IAM SigV4 (no API key to manage) but require: `bedrock:InvokeModel` added to the Lambda execution role's inline policy (new grant, same shape as the existing `thejudge-openai-secret` policy but for a different action), per-region model-access enablement in the Bedrock console/account (an operational step outside code), and a second provider integration to test and maintain. Given the corpus is small (3,432 rule entries, ~823K chars) and this is a build-time job, the *volume* cost difference between providers is minor; the plumbing-reuse argument dominates for a first cut. Revisit Bedrock only if a second reason emerges (e.g., data-residency, or Titan/Cohere already adopted for the answer-generation model itself).
**Risk:** None of this is decided in the repo today — flagged as an open question below, not a settled recommendation, since it's a provider choice the owner should make explicitly.

### RA-003 — Chunk the Comprehensive Rules corpus above rule-entry granularity, keep rulings separate and much smaller in scope — with-rag
**Current -> Target:** Today's `gameRulesRuleIndex.json` entries are one row per rule number (3,432 entries, avg 240 chars — e.g. `100. General` is a 13-char entry). That granularity is fine for exact/parent rule-ID matching but is too fragmentary for embedding quality (very short chunks embed poorly and fragment related sub-rules like `702.1`-`702.19` keyword definitions across dozens of near-duplicate vectors). Target: chunk at a coarser unit — likely full numbered section (e.g. all of `702.x` deathtouch/lifelink/etc. keyword-ability text together) or a fixed token window with rule-boundary-aware splitting, sized for the embedding model's sweet spot (roughly 200-500 tokens per chunk is typical for retrieval quality).
**Gap:** No chunking strategy exists beyond "one row per existing rule number," which was designed for lexical/IDF scoring, not embedding.
**Services/tradeoff:** Re-chunking is a data-pipeline change only (same offline job as RA-001), no new AWS service. The card-rulings corpus (76,605 entries, 19.5 MB) is a much bigger embedding volume if included — recommend scoping the first RAG pass to the **rules corpus only** (823K chars, cheap) and treating rulings semantic search as a separate, later decision, since System 1 today is exact-match lookup for submitted cards only, not a "search rulings by topic" feature at all.
**Risk:** Coarser chunks reduce precision on very specific rule-ID lookups that the current exact-match bonus (`SCORE_EXACT_RULE_ID = 100`) handles well today — the hybrid design (RA-004) needs to preserve that exact-match path so chunking doesn't regress a case System 3 already gets right.

### RA-004 — Hybrid fusion, not vector-only replacement — with-rag
**Current -> Target:** Today's scoring already blends multiple signals in one formula (IDF + question/keyword multipliers + exact/parent rule-ID bonuses). Target: keep that shape — add a vector-similarity signal fused with the existing lexical/exact-match signals (e.g. reciprocal rank fusion or a weighted sum of normalized BM25/IDF score and cosine similarity), rather than deleting lexical scoring in favor of vectors alone.
**Gap:** No fusion logic exists; this is new code in `gameRulesRetrieval.ts`'s scoring path (`scoreEntry`/`scoreIndex`).
**Services/tradeoff:** Pure vector retrieval alone tends to miss exact rule-number queries and precise keyword matches that the current `SCORE_EXACT_RULE_ID`/keyword-vocabulary boosts nail today (a player citing "702.19b" should always resolve exactly, not depend on embedding proximity). Hybrid keeps that guarantee while adding recall for paraphrased/semantic questions the current IDF-only approach can miss (e.g. a question that doesn't share vocabulary with the rule text at all). No new AWS service required for fusion itself — it's application code; only the embedding step (RA-001/002) and index storage (RA-005) touch infrastructure.
**Risk:** Tuning two signals into one score reintroduces the same tuning burden DEC-046 already solved once for lexical-only scoring (question/keyword multipliers were hand-tuned). Budget real iteration time against the eval harness, not a one-shot cutover.

### RA-005 — Bundle the vector index as a static file in the Lambda package; no managed vector DB yet — now / with-rag
**Current -> Target:** Today all System 2/3 data ships inside the Lambda zip via `scripts/package-lambda.sh` (verbatim copy of `apps/backend/data`), loaded into in-memory `Map`/array caches at cold start with zero network I/O in the hot path. Target: keep that pattern — ship a precomputed vector index (e.g. flat float32 arrays + a brute-force or approximate in-memory index like `hnswlib-node`, or a serialized structure loaded once) as a new file in `apps/backend/data`, not a call to OpenSearch Serverless, Pinecone, or a Bedrock Knowledge Base.
**Gap:** No vector index format or loader exists yet.
**Services/tradeoff:** The rules corpus is small (3,432 chunks even before re-chunking) — a brute-force in-memory cosine-similarity scan over a few thousand vectors is fast enough (sub-millisecond to low-millisecond) and fits the existing cold-start-load, scale-to-zero, no-external-dependency design that keeps this Lambda cheap and simple. A managed vector store (OpenSearch Serverless, Pinecone, Bedrock Knowledge Bases) adds a persistent, always-on-priced backing service that fights the whole point of the current architecture (scale-to-zero, reserved concurrency 5, no idle cost) for a corpus this small — that tradeoff only flips if the corpus grows by orders of magnitude (e.g. rulings are added to the semantic index too, or a broader corpus like tournament rulings/judge Q&A is added later). At `text-embedding-3-small`'s 1536 dims, 3,432 rule chunks is roughly 3,432 × 1536 × 4 bytes ≈ 21 MB raw float32 — trivial against the 250 MB unzipped budget and the 512 MB Lambda memory ceiling, even loaded fully in-process alongside the existing ~50-55 MB package. If rulings are later added to the semantic index (76,605 entries), re-check this arithmetic — that's roughly 20x the vector volume.
**Risk:** In-memory brute-force scoring adds to cold-start load time and per-invocation memory footprint on top of the existing IDF/keyword caches — should be measured against the 512 MB ceiling and cold-start budget once a real chunk count and dimension are chosen, not assumed safe.

### RA-006 — No reranking pass for the first cut — later
**Current -> Target:** Today there is no reranking step — System 3's own score *is* the final rank. Target: leave it that way initially; add a cross-encoder reranker (e.g. Cohere Rerank, or a small local model) only if hybrid fusion (RA-004) demonstrably under-performs on the eval harness after tuning.
**Gap:** Nothing to build now; this is a deferral, not a missing capability blocking RAG.
**Services/tradeoff:** A reranking pass is another network call (or another bundled model) in the request hot path, adding latency and cost against the same 20 s timeout and cost-conscious scale-to-zero design, for a corpus (3,432 rule chunks) small enough that fused first-stage retrieval likely suffices. Revisit only with eval evidence, not preemptively.
**Risk:** None near-term; flagging so it isn't silently scoped into the first RAG slice.

### RA-007 — Extend the eval harness's recall/noise checks to survive non-deterministic vector scores — with-rag
**Current -> Target:** Today's harness (`contextEvaluationHarness.ts`, `relevanceReport.test.ts`) checks exact rule-ID recall/noise against a deterministic scorer, and separately snapshots exact prompt text (`.prompt.golden.txt`). Both assume System 3's output is a pure function of static IDF tables — reproducible byte-for-byte. Target: keep the recall/noise **contract** (expected rule IDs present, forbidden rule IDs absent, top-5 cap) but stop asserting exact match on raw similarity scores, and treat exact-string prompt snapshots as batch-updated goldens rather than hand-authored ones once the supplemental section's *scores* (not rule-ID selection) become embedding-derived.
**Gap:** The harness's design already anticipated labeled expected/forbidden sets (DEC-047) — that structure survives. What doesn't survive is any assumption that a given query always yields bit-identical scores, since embedding calls (even the query-only one, RA-001) introduce provider-side nondeterminism unless pinned.
**Services/tradeoff:** No new AWS service. Recommend either (a) fixture-pin the query embeddings (store precomputed vectors for each eval fixture's question, bypass the live embedding call in tests, same pattern the harness already uses for static topic/rule data) to keep the harness fully deterministic and CI-safe, or (b) keep it recall/noise-only (already the DEC-047 pattern) and drop exact-score assertions. Option (a) is stronger and cheaper than it sounds — the eval fixtures are static text, so their embeddings can be computed once and checked in like any other fixture data.
**Risk:** If this isn't done before RAG ships, `quality-check.yml`'s `npm run test:scripts`/typecheck-lint-format-test gate either breaks on live-provider nondeterminism or silently stops testing retrieval quality — either outcome is worse than doing this alongside RA-001-004, not after.

### RA-008 — Do not fold `compare-combo-answer-quality.mjs` into rules-retrieval eval — later
**Current -> Target:** That script is scoped to combo-enrichment answer comparison (REQ-146, DEC-161) — informational, opt-in, never gates a build, unrelated to `gameRulesRetrieval.ts`. No change needed for RAG; noting this so a future pass doesn't conflate the two eval surfaces.
**Gap:** None — this is a scope clarification, not a gap.
**Services/tradeoff:** N/A.
**Risk:** Low; included only to prevent the RAG work from accidentally growing that script's scope instead of extending `contextEvaluationHarness.ts`.

## Open questions

- **Embedding provider**: this study recommends OpenAI embeddings for plumbing-reuse reasons (RA-002), but that's an architecture-fit argument, not a cost/quality benchmark — the owner should confirm against actual retrieval-quality numbers once a chunking strategy (RA-003) is fixed, not take RA-002 as final.
- **Rulings in scope or not**: should the semantic index cover only the 3,432-entry rules corpus, or eventually the 76,605-entry rulings corpus too? This changes the vector-store-vs-bundled-file tradeoff in RA-005 by roughly 20x in volume and is a product-scope call (does "RAG for rules" mean rules-text grounding, or also surfacing relevant historical rulings semantically, beyond System 1's current exact per-card lookup?).
- **Chunk boundary granularity** (RA-003): full numbered section vs. fixed token window vs. some rule-hierarchy-aware split — needs a labeled quality comparison against the eval harness, not a guess from this study.
- **Q-001** (pre-existing, from `system-map/game-rules-retrieval.md`): the keyword-vocabulary derivation strategy is still open and unresolved independent of this study; RAG work should note whether it inherits or retires that vocabulary once hybrid fusion (RA-004) has its own keyword-signal path.
